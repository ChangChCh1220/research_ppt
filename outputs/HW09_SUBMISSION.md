## 一、專案簡介

### 1. 專案背景與痛點
本專案為國立陽明交通大學土木工程研究所碩士論文——《**光達輔助弱監督之四維雷達可靠度估計與功率抑制**》（*LiDAR-Assisted Weakly Supervised Reliability Estimation and Power Suppression for 4D Imaging Radar*）的核心學術研究知識庫與動態簡報生成系統。

在傳統學術研究與網頁開發中，往往面臨兩大痛點：
1. **RAG 檢索的碎片化與幻覺**：每次向 AI 提問都從零搜尋，AI 容易在龐大且未經消化的論文點雲中產生「看似合理卻缺乏物理依據」的幻覺。
2. **一次性生成（Vibe Coding）的不可持續性**：先前常見的 Vibe Coding 模式往往只求「把當下這個網頁趕快兜出來」，但程式碼缺乏統一架構、命名混亂，當兩週後想要新增一篇新論文或補充一組消融實驗簡報時，AI 往往風格跑版、JS 邏輯崩潰，必須全部重寫。

### 2. 核心架構與哲學
本專案參考知名 AI 學者 Andrej Karpathy 的 **LLM Wiki** 模式與軟體工程規範，制定了嚴格的 **三層架構**（Three-Tier Architecture）：
- **層 1：`raw/`（原始資料層）**：不可變（Immutable）的唯一真實來源（Source of Truth），收錄 16 篇 CVPR/AAAI/IEEE 頂級論文原始 PDF、作者碩論初稿與實驗數據。
- **層 2：`wiki/`（知識層）**：由 AI 全權編譯與維護，包含 16 篇來源結構化摘要、9 大核心概念、7 大實體模型與 5 篇跨來源橫向技術對比。**知識只編譯一次並持續維護，而非每次提問都重新檢索。**
- **層 3：`outputs/`（應用輸出層）**：由 AI 嚴格僅依 `wiki/` 知識編譯出的專題研究筆記、逐頁講者腳本、以及單檔自包含 HTML 簡報，絕不反向污染原始資料。

### 3. 網頁成果特色
專案根目錄部署了全景導覽門戶 [`index.html`](index.html)，並已藉由自定義規則擴充至 **10 份高精度自包含 HTML 簡報**（共 98 頁 Slide），全面採用統一的 **冰川極簡藍白（Glacial Tech Minimal）** 設計語言：
- **自包含（Self-contained）**：單檔純 HTML，無須 Node.js 後端伺服器，直接用瀏覽器即可離線或線上流暢開啟。
- **學術級 KaTeX 數學渲染**：完美支援行內 `$...$` 與區塊 `$$...$$` LaTeX 公式。
- **全方位演講互動功能**：16:9 比例畫布、進度條、鍵盤翻頁（`←` / `→` / `Space`）、講者備忘錄抽屜（按 `S` 鍵開關）、全螢幕切換（按 `F` 鍵）與 `@media print` 完美列印 PDF 樣式。
- **首頁即時檢索與分類過濾**：提供即時關鍵字搜尋與「碩士論文系列」、「弱監督與教師」、「特徵與網路」、「功率抑制與選模」、「大車衰退與診斷」、「演算法深入改良」、「補充實驗清單」7 大標籤過濾。

2. **`wiki/`（LLM 全權維護）**：所有摘要、概念頁、實體頁、比較分析與連結皆由 LLM 建立與更新，保持結構一致與交叉連結完整。

4. **`AGENTS.md`（共同演進）**：當工作流程、分類或格式需要調整時，經與使用者確認後更新本文件。

## 二、格式與命名規範

### 1. 檔名與連結規則
- **檔名格式**：使用清晰、無歧義的英文或中英混合小寫短橫線命名（`kebab-case`），或一致的標準名稱（例如 `deepseek-r1.md`、`kv-cache.md`、`2024-rag-survey.md`），避免空白字元與特殊符號。
- **內部連結**：統一使用 Obsidian 相容的雙括號 Wikilinks，例如 `[[kv-cache]]` 或 `[[deepseek-r1|DeepSeek-R1]]`，以便 Obsidian Graph View 正確呈現知識網絡。
- **引用出處**：Wiki 頁面中的關鍵數據、主張或結論，必須以 Wikilink 標註來源頁面（例如：`見 [[2025-deepseek-r1-paper]]`）。

### 2. YAML Frontmatter（支援 Obsidian Dataview）
每個 `wiki/` 下的 Markdown 頁面都應包含標準 YAML frontmatter：
```yaml
---
title: 頁面標題
type: concept # 可選值: overview | source | concept | entity | comparison
tags:
  - llm-research
  - inference
created: YYYY-MM-DD
updated: YYYY-MM-DD
sources_count: 1
status: active # 可選值: seed | active | superseded
---
```

### 3. LaTeX 數學公式規範
- 全知識庫（`wiki/`、`outputs/notes/` 與 HTML 簡報）皆須支援標準 LaTeX 數學語法：行內公式使用 `$...$`，獨立區塊公式使用 `$$...$$`。

## 三、核心頁面範本

### A. 來源摘要頁（`wiki/sources/`）
- **書目與基本資訊**：作者 / 機構、發表年份、連結或 arXiv ID、原始檔案路徑（`raw/...`）
- **一句話總結（TL;DR）**
- **核心問題與動機**：想解決什麼痛點？
- **關鍵方法與技術細節**：核心架構、公式或演算法機制
- **主要實驗結果與限制**：關鍵數據、對比基線（Baselines）、作者承認或觀察到的限制
- **知識庫關聯與衝突**：與現有 `[[concepts]]` / `[[entities]]` 的連結；是否強化、補充或推翻/矛盾先前的觀點？

### B. 概念頁（`wiki/concepts/`）與實體頁（`wiki/entities/`）
- **定義與定位**：這個技術/模型/基準是什麼？解決什麼問題？
- **核心機制 / 演進脈絡**：依時間或技術演進整理
- **代表性工作與實作**：關聯的模型、論文或工具（附上 Wikilinks）
- **優缺點與權衡（Trade-offs）**
- **矛盾與開放問題**：不同來源間存在分歧的觀點，或尚未解決的研究問題
- **參考來源**：條列所有貢獻到此頁面的 `wiki/sources/` 頁面

### C. 比較與專題分析頁（`wiki/comparisons/`）
- 用於橫向比較多種技術或從 Query 沉澱出的研究綜合報告。
- 包含：比較維度總表、適用場景建議、關鍵差異分析與來源引用。

## 四、四大核心操作流程（Operations）

### 1. Ingest（攝入新資料）
1. 保存原始資料至 `raw/` 對應子目錄；完整閱讀原始文件。
2. 建立來源摘要頁至 `wiki/sources/`。
3. 編譯並更新相關概念頁、實體頁與比較頁，主動標註矛盾與演進。
4. 更新 `index.md` 與追加 `log.md`。

### 2. Query（查詢與知識沉澱）
1. 先讀 `index.md` 定位相關頁面，深入讀取 `wiki/`，必要時才核對 `raw/`。
2. 整合跨頁面知識給出深入回答，標註出處；主動回寫新洞見至 `wiki/comparisons/`。

### 3. Lint（健康檢查與維護）
1. 矛盾與過時檢查：標註被推翻的舊宣稱。
2. 圖譜檢查：揪出孤島頁面（Orphans）、缺漏概念（Missing Concepts）與斷鏈。
3. 在 `log.md` 追加紀錄。

### 4. Research-to-Slides（研究筆記與 HTML 簡報生成）
同一主題共用 `YYYY-MM-DD-<topic-slug>` 檔名前綴，依以下三階段執行：
1. **產出研究筆記（`outputs/notes/`）**：
   - **嚴格僅用 Wiki 內容**：筆記正文與核心論述 100% 僅能依據 `wiki/` 既有頁面撰寫，並以 `[[頁面名稱]]` 標註來源；Wiki 尚未涵蓋之缺口誠實標註 `[Wiki 尚無此部分資料]`，絕對不可將外部搜尋內容寫入正文。
   - **上網搜尋與可下載建議文獻**：主動上網搜尋相關論文，統一列於筆記最末節「建議參考文獻（待 Wiki 化）」，並優先附上可直接點擊下載的 PDF 連結。
2. **產出簡報逐頁腳本（`outputs/slide-scripts/`）**：
   - 拆分為逐頁投影片大綱（含頁標題、精簡條列重點、圖表/公式視覺設計與講者口白備註）。
3. **產出 HTML 簡報（`outputs/slides/`）**：
   - 依逐頁腳本產出單檔自包含 `.html` 簡報，採用 **冰川極簡藍白（Glacial Tech Minimal）** 風格：
     - 純白畫布（`#FFFFFF`）搭配極淡點陣底紋、冰藍卡片（`#F4F8FF` / `#EFF6FF`）、深海藍主文字（`#0F172A`）、科技藍強調色（`#2563EB`）與 1px 淺藍灰細邊框。
     - 16:9 簡報畫布、內建 KaTeX 支援 LaTeX 公式、鍵盤 `←/→/Space` 翻頁、進度條與頁碼、`S` 鍵切換講者備註面板、`F` 全螢幕、以及 `@media print` 友善列印匯出 PDF 樣式。
     - **語法安全規範**：在 JS 模板字串內一律使用 `<code>...</code>` 代替反引號，並嚴格跳脫 LaTeX 反斜線，杜絕語法崩潰。
4. **日誌紀錄與首頁掛載**：更新 `index.html` 插入新簡報卡片，並於 `log.md` 追加紀錄。

## 五、深度說明：如果之後要新增一個新的頁面或內容，這套規則如何幫助 AI 繼續完成？

這份作業的核心目的並非只是一次性的「把網頁刻出來」，而是**建立一套可複製、可持續延伸的軟體工程規則（Schema），讓 AI 成為有章可循的知識編譯器與網頁架構師**。

當未來有新的研究需求、需要新增一個頁面或一組簡報時，本專案設計的規則透過以下四個維度，引導 AI 高效、零失誤地完成任務：

### 1. 嚴格的「單一真實來源」與「防幻覺因果鏈」
- **規則約制**：在第四章 `Research-to-Slides` 流程中，我們強制規定：**「研究筆記的正文內容 100% 只能依據 `wiki/` 既有頁面撰寫」**。如果 AI 遇到未入庫的新概念，被明文禁止憑空編造數據，必須誠實標註 `[Wiki 尚無此部分資料]`，並將外部論文列於文末「建議參考文獻（待 Wiki 化）」。
- **對 AI 擴展的幫助**：這徹底切斷了大型語言模型隨意胡謅、數值漂移（Hallucination）的劣習。當使用者要求新增一個主題時，AI 會主動依照因果鏈執行：
  $$\text{檢索下載論文至 raw/} \longrightarrow \text{編譯結構化摘要至 wiki/} \longrightarrow \text{依據 wiki 撰寫嚴謹筆記} \longrightarrow \text{生成精確對應的 HTML 簡報}$$
  保證未來新增的第 11 份、第 20 份簡報，裡面的每個數據與公式都能在 Wiki 中溯源。

### 2. 精確的「設計契約（Design Contract）」杜絕前端樣式漂移
- **規則約制**：文件在第四章第三節嚴格定義了前端視覺系統——**「冰川極簡藍白（Glacial Tech Minimal）」**，具體鎖定了十六進位色票（純白底 `#FFFFFF`、冰藍卡片 `#F4F8FF`、海軍藍文字 `#0F172A`、科技藍強調 `#2563EB`）、16:9 比例畫布、KaTeX 依賴注入方式，以及**關鍵語法安全規則（禁止在 JS 模板字串內使用 Markdown 反引號，改用 `<code>...</code>`，並對 LaTeX 符號雙重跳脫）**。
- **對 AI 擴展的幫助**：AI 在編寫前端程式碼時最容易「自我發揮」導致頁面風格前後矛盾，或因模板字串語法錯誤導致整頁白屏。本規則就像一套嚴格的 UI Component Library，任何 AI（無論是 Claude、GPT 還是 Gemini）只要閱讀了本規範，產出的新簡報都能在第一時間達到像素級的視覺統一與 100% 語法無誤。

### 3. 三步自動簿記（Automatic Bookkeeping）維持全域圖譜完整
- **規則約制**：文件強制要求，任何新增內容均不可成為孤立的「檔案孤島（Orphans）」，AI 必須在完成生成後自動執行三步驟閉環：
  1. 在 `index.md` 登記該頁面的雙向 Wikilink 與一句話摘要。
  2. 在全景門戶 `index.html` 插入對應的 `<article class="presentation-card">`，並打上主題檢索 Tag。
  3. 在 `log.md` 末尾以只增不減（Append-only）的方式追加一筆稽核紀錄。
- **對 AI 擴展的幫助**：這免除了人類手動整理目錄的負擔。AI 每擴展一個新概念或新簡報，整個知識庫與線上網站就會自動同步更新，永遠保持內容與首頁的一致性。

### 4. 經得起考驗的擴展性實證（Extensibility Proof）
